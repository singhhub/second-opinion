Architecture comparison

Two Embeddings, One Pattern

The Dating App's pgvector setup and the medical RAG pipeline we're planning for LLM Council share the exact same embedding call and index — that part gets copied, not reinvented. What changes is the shape of the data around it: one embedding per person versus many embeddings per document, and what happens to the result once it's retrieved.

Carries over unchanged

  • Postgres + pgvector, same <=> cosine operator
  • Same embedding call: Gemini embedContent, gemini-embedding-001, 768 dimensions
  • Same HNSW index shape and tuning (m=16, ef_construction=64)
  • Same lazy re-embedding guard — hash the source text, skip the API call when nothing changed

Reshaped for retrieval

  • One row per person → a separate table, many chunks per document, keyed by patient
  • A 0.75 similarity floor that can legitimately return zero matches → no floor, always return the best-available top-K
  • Ranked list shown straight to the user → chunks feed your existing 3-stage council before anything reaches a caregiver

The floor removal in row 6 is the one decision worth pausing on: a dating match with weak similarity should be hidden, but a medical question with only a weak-similarity record still deserves the model's best attempt at an answer — silence isn't a safer failure mode here. Retrieval always returns its top-K; if nothing is truly relevant, that's a judgment for the chairman synthesis to surface, not for the SQL layer to hide.
